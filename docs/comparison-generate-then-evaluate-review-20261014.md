# 全クラスタで比較記事を作成してから除外・採点する方式の検討とAPI費用

作成日：2026-10-14。設計検討とオフライン費用計算のみ。新しい比較記事の生成、API推論、本番手順の変更は行っていない。

更新：ユーザーの追加方針を反映した。[不適記録・選び直し・採点方式選定の評価計画](comparison-generate-then-evaluate-experiment-plan-20261014.md)を最新の設計方針とする。2方式の比較は構築時だけで、本番では一方のみを実行する。第4節の費用は前回の仮定による履歴で、両方式の比較実験費用や選び直し後の事実整理費用を含む新しい実績ではない。

## 1. 判断

生成・検証の役割：生成モデルも「3者が別対象か」「共通の判断目的があるか」「原資料にない説明を加えていないか」を明示的に確認する。その上で、生成モデルと異なる評価モデルが同じ項目を再検証し、モデルによる見落とし・誤判断の追加検出を図る。

目的を明確化：最適な比較記事をできるだけ多く得ることではなく、問題のない比較記事をいくつか得ることを優先する。少数の取りこぼしは許容し、疑義が解決しない記事を無理に採用しない。生成と評価の両方で見落とす可能性は残るため、評価に必要な原文根拠を引き継ぐ。詳細は最新の評価計画に記載した。

提案方式は有望である。クラスタごとに3記事を選んで初稿を作り、実際の比較内容で適否を判定すれば、事前の抽出状態や比較項目の完全一致によって、役立つ記事まで落とす問題を減らせる。元提案のクラスタ内全ペアLLM判定（最大1,969組）も省ける。

ただし、全クラスタで生成を試すことと、全クラスタから必ず1本公開することは分けて設計する。比較の意義が弱いクラスタは不採用を許し、最初の3記事の組合せが悪い場合は、別の組を試す余地を残す。

先の完成記事評価では、帳票入力90点、IoTゲートウェイ89点に対し、水インフラ監視65点となった。表現が破綻しないことと、読者の判断に役立つことには差がある。一方、この点数は作成にも関わったCodexの編集評価であり、新方式の効果を証明する独立実験ではない。

## 2. 主な問題と対処

|問題|影響・今回の例|対処|
|---|---|---|
|最初の3記事で品質が決まる|良いクラスタでも1件だけ用途が離れると弱い記事になる|MMR等で簡単に選び、生成・評価で分かった不適理由を反映して最大1回選び直す。2組目も不適なら却下する|
|文章が比較の弱さを隠す|水槽・池・配管を「水の監視」とまとめても、必要なものが設備で決まりやすい|「誰が何を決める比較か」「3者目で判断がどう変わるか」を具体的に評価する。比較不成立の出力を許す|
|同じ発表・製品を3枠に重ねる|C07のF809/F876は別社配信の同じ協業成果|生成時に「比較不適」、該当ID・理由・原資料の根拠を記録し、後段で除外する。生成側の見逃しは別途評価する|
|完成記事間の重複を見落とす／除外しすぎる|別クラスタでも同じ比較になる一方、同分野でも判断目的が違えば別記事の価値がある|タイトルや文章類似度だけで決めず、比較対象・読者の問い・主要な結論の重なりで確認する|
|完成文だけでは事実を検証できない|根拠のない機能や条件違いも自然な文章にできる|原資料と引用位置を渡し、事実の合否と編集品質点を別項目で出す。根拠不備は高得点でも採用しない|
|全記事一括評価は点検しにくい|30本の本文と全原資料は入力が大きくなり、個別の根拠確認も難しくなる|一括採点と個別採点後の全体確認を構築時に同じ記事で試し、妥当性・安定性・費用を比べて本番方式を一つ選ぶ|
|相対順位だけでは弱い記事でも1位が出る|全候補が低品質でも順位は付く|公開の最低条件と、合格記事間の順位を分ける。今の20本の点数だけから閾値を即決しない|
|採点者の好み・採点の揺れがある|長さや流暢さが比較価値に置き換わり得る|元順位・MMR値を伏せ、各評価軸に本文根拠を必須とする。境界例だけ別判定や人のサンプル確認へ回す|
|不採用初稿にも費用がかかる|採用本数は生成本数より少なくなる|再生成に上限を設け、採用1本当たりの費用も記録する|

重複は、(a) 元記事の同じ発表・製品、(b) 1本の比較枠の同じ対象、(c) 完成記事同士の同じ比較内容、の3段階で確認する。URL・本文ハッシュ等で明確に分かるものは生成前に整理すると無駄が少ない。意味上の重複は原資料を伴う後段の評価で確認する。ベクトル類似度は確認候補を絞る指標として使い、同一性の確定には使わない。30記事の全435ペアを必ずLLMへ送る必要はない。

PR TIMESは指定どおり異なる企業IDを統合せず、各IDの最新記事を選ぶ。その上で同じ製品・共同発表に対応する記事を追跡し、比較対象として重ねない。元の配信IDと記事の来歴は保持する。

## 3. 追加方針を反映したフロー

1. 各配信IDの最新記事を選び、従来と同じ方法で埋め込み・クラスタリングする。
2. 各クラスタから既存ベクトルのMMR等で3記事を簡単に選ぶ。全記事のLLM構造化や全ペア適否判定は標準工程に戻さない。
3. 生成モデルは原資料を読み、別対象・共通の判断目的・原資料への忠実さを明示的に点検しながら比較本文を作る。不具合を見つけたら「比較不適」と理由・該当記事ID・根拠を明示する。無理に正常な比較本文を完成させず、不適結果として返してよい。
4. 後段では不適の記録を確実に除外へ反映する。生成モデルと異なる評価モデルが、原資料と完成記事から同じ3項目を再検証する。生成側の見逃しの追加検出と、不適記録の処理漏れは分けて測る。
5. 不適であれば理由を使って3記事を1回だけ選び直す。初回を含め最大2組で、2組目も適切にならなければ却下する。全体の重複確認で不適となった場合も追加の選び直し枠を設けない。
6. 採点方式は構築時にA「全記事一括」とB「個別採点後に全体の重複・採点整合を確認」を比較する。本番では選定した一方のみを使い、不適を除外した上で順位を出す。
7. 原文ハッシュ、3記事ID、試行回数、生成側・評価側の不適理由、モデル・プロンプト版、採点根拠、使用量を保存する。

「資料で確認できず」は非対応を意味しない、という注記は、比較表に「資料で確認できず」がある場合にだけ入れる。

抽出のunknownや共通項目の完全一致をそのまま後段の不合格条件に戻さない。異なる方式でも具体的な判断に役立つかを評価し、共通の判断がないものを除外する。採点Aが不安定だとは未確定であり、方式の詳細・比較指標・本番への選定条件は[評価計画](comparison-generate-then-evaluate-experiment-plan-20261014.md)に定める。

## 4. 公式単価と計算の前提

2026-10-14に公式ページを確認。過去と同じモデルの標準テキスト料金を使用する。以下は米ドル、100万トークン当たり。

|モデル|入力|キャッシュ入力|出力|用途|
|---|---:|---:|---:|---|
|gpt-4.1-mini-2025-04-14|$0.40|$0.10|$1.60|事実整理・初稿・修正|
|gpt-4.1-2025-04-14|$2.00|$0.50|$8.00|検証・品質採点・全体確認|
|text-embedding-3-small|$0.02|—|—|埋め込み|

出典：[GPT-4.1 mini](https://developers.openai.com/api/docs/models/gpt-4.1-mini)、[GPT-4.1](https://developers.openai.com/api/docs/models/gpt-4.1)、[text-embedding-3-small](https://developers.openai.com/api/docs/models/text-embedding-3-small)。

公式モデルページにはGPT-4.1系のDeprecated表示がある。この試算は従来モデルの継続利用を仮定した比較用であり、運用モデルを変更する場合は、利用可否・品質・使用量・単価を改めて確認する。今回、API接続による利用可否確認は行っていない。

料金 = 入力トークン数 × 入力単価 / 1,000,000 + 出力トークン数 × 出力単価 / 1,000,000。将来見積もりではキャッシュ割引を仮定していない。

### 4-1. 過去20本の使用ログから求めた実績相当額

各記事のexecution-summary.jsonのusageを再集計した。請求書照合ではなく、使用量と単価からの推定額である。

|工程|呼出数|入力合計|出力合計|推定額|
|---|---:|---:|---:|---:|
|初稿生成・mini|20|122,026|30,820|$0.0981224|
|根拠検証・4.1|20|263,810|23,354|$0.7144520|
|追加の検証・4.1|1|12,934|998|$0.0338520|
|合計|41|398,770|55,172|$0.8464264|

追加検証を除くと20本で$0.8125744。同じ平均使用量で30本なら、初稿$0.1471836、根拠検証$1.0716780、計 **$1.2188616（約$1.22）**。過去と同じ追加検証率まで比例換算すると約$1.27。

これまでの初稿にはCodexが原文確認して作った事実パッケージを使い、検証前にはチャット内で編集した。前回の100点評価もチャット内のCodex評価であり、API採点ではない。したがって約$1.22は、事実整理・編集・品質採点を全て含めた完全自動処理の費用ではない。

### 4-2. 30クラスタを自動処理する試算

チャット内で行っていた事実整理・品質採点・修正もAPIへ移す例。初稿の行を除き、下記トークン数と修正率は新しい実測値ではない。入力は指示・スキーマ・原資料・必要な記事本文を含む総量を想定する。

|工程|モデル|回数|1回の入力／出力トークン|見積額|
|---|---|---:|---:|---:|
|選んだ3記事の事実整理|mini|30|15,000／4,000|$0.3720|
|初稿生成|mini|30|6,101.3／1,541（過去平均）|$0.1472|
|原資料との検証＋品質採点|4.1|30|15,000／2,000|$1.3800|
|全体の重複確認・採点の調整|4.1|1|25,000／2,000|$0.0660|
|同じ3記事で本文修正|mini|6|10,000／2,500|$0.0480|
|修正後の検証・再採点|4.1|6|15,000／2,000|$0.2760|
|合計|—|103|—|**$2.2892（約$2.3）**|

初回30本、うち20%を1回修正する例。全体確認には対象・目的・評価理由の構造化要約と疑わしい重複の根拠を渡す。全30本の原資料を一括投入する想定ではない。疑義の多さや入力長により追加照合が必要になる。3記事を選び直して事実整理からやり直す場合も追加費用となる。

当初の予算感は **30クラスタ1回につき約$2〜$4**。これは統計的な信頼区間や保証上限ではなく、上記モデル・文章量・少数回の修正を前提にした計画目安である。長文資料、複数組の再生成、追加の独立評価を増やせば超える。採用本数をK本とすると採用1本当たりは$2.2892/K。10本採用なら約$0.23/本、20本なら約$0.11/本となる。

### 4-3. 埋め込み、Batch、対象外費用

- 保存済み元記事のベクトルを使う今回の比較では、埋め込みの追加費用は$0。クラスタリング・MMR・ローカルのハッシュ比較にOpenAI料金は発生しない。新しい元記事の埋め込みは別途必要で、text-embedding-3-smallなら100万入力トークンにつき$0.02。
- 完成比較記事にも重複候補抽出用の埋め込みを付ける場合、30本合計60,000トークンという仮定なら追加$0.0012。上記$2.2892には含めていない。
- [Batch API](https://developers.openai.com/api/docs/guides/batch)は同期API比で入力・出力が50%割引。上記全工程が対応し実際にBatchへ回せる場合、計算上は約$1.14となる。各バッチは24時間の処理枠で、整理→生成→検証→修正の依存関係ごとに分けるため、全工程が24時間以内とは見込まない。
- サーバー、収集、画像、検索ツール、税、為替・決済手数料、人の確認、およびチャット側の利用料金は含まない。

## 5. 対象数と検証方法

30クラスタは、旧665記事による保存済み結果を費用例に用いた数である。企業IDを統合しない方針に直した最新選択は666記事であり、それを再クラスタリングした結果のクラスタ数・所属・C番号はまだ確定していない。実運用では新しいクラスタ数に応じて再計算する。

新旧方式は同じ入力・クラスタ・評価基準で比べる。採用本数、採用記事の品質、事実不備率、重複の見逃しと過剰除外、選び直し率、採用1本当たり費用を記録する。今回の20本は調整用に使い、未使用クラスタや別日の記事で再確認する。
