# Extraction仕様：AI・IoT記事の候補語DB検索とカウント

更新日：2026-10-13。タイトル除外方針：`extraction-title-keywords-v3-20261013`。分野方針：`extraction-ai-iot-v2-20261013`。

## 目的と処理順序

Discoveryのlabel・aliasesを対象記事のタイトル・本文から文字列検索し、記事ごとに含まれる異なる候補の数と語の一覧を示す。Extractionは値・根拠・条件の抽出や意味判定を行わず、AIを呼び出さない。

1. AIまたはIoTの分野の一覧だけを収集する。収集はPR TIMESのAI／IoTキーワード検索を使用する。各検索の公開結果上限に達しても必要件数に不足する場合、AI分野の別表記（人工知能、機械学習、LLM、AIoT）でも補充する。一般ニュースリリース一覧は使用しない。
2. 一覧タイトルに111語のいずれかが含まれる記事を除外し、本文取得を省く。
3. 通過記事の公開HTMLを取得し、公式の「種類」が商品サービス（種類ID 01）であることを確認する。種類が異なる、または確認できない記事は採用しない。実際のタイトルを再判定し、タイトル・本文冒頭でAI／IoTの記載を確認する。見出しに置換文字（�）がある場合は、同じ公式HTMLの正常なJSON-LDまたはog:titleで回復し、欠損文字を推測して補完しない。
4. 分野条件を満たす記事だけを検索用SQLite DBへ保存する。除外記事のID・URL・タイトル・理由は別に記録する。
5. 除外後の対象200件以上を確保する。既定の最低件数200は検索可能な対象だけで判定し、不足時は集計を中止する。
6. Discovery語彙もDBへ登録し、保存済みDBに対して候補語を検索・カウントする。

AIとIoTは和集合とする。両方を含む記事も1記事として数える。domain-labelをAI／IoTと名付けただけの一般記事を受理することはない。

## AI／IoTの分野判定

タイトル、または本文の先頭1200文字に次の語がある記事を受理する。本文に会社概要・企業概要・会社紹介・企業紹介・会社情報・企業情報の見出しがあれば、その見出し以降を分野判定へ含めない。

| 分野 | 判定語 |
| --- | --- |
| AI | AI、人工知能、機械学習、ディープラーニング、深層学習、LLM、大規模言語モデル、AIoT、artificial intelligence、machine learning |
| IoT | IoT、Internet of Things、モノのインターネット、AIoT |

英数字語には英数字・アンダースコアとの境界を設ける。APIやThailand中の文字列をAIとして扱わず、IoTivityをIoTとして扱わない。全角ＡＩも正規化して扱う。AIoTは両分野に該当する。

この条件は記事本文全体の意味分類ではなく、本文冒頭の明示的な分野語で絞るための文字列規則。確認用JSONには各記事のdomainsとmatched_domain_termsを保存する。候補語の一致・カウント自体は、受理した記事のタイトルと本文全体を検索する。

## DB保存と検索対象からの除外

| テーブル | 保存内容 |
| --- | --- |
| term_corpora | 記事群ID・分野名 |
| term_articles | 対象記事の元のタイトルと本文、正規化文章、ハッシュ、除外フラグ・分野フラグ・方針版 |
| term_title_exclusions | タイトルで除外した記事のID・URL・タイトル・一致した全除外語・方針版 |
| term_domain_screenings | AI／IoTの分野判定、判定語、タイトル・URL・方針版。分野外も記録する |
| term_vocabularies / term_candidates | Discovery語彙・ハッシュ、各候補とlabel・aliasesの検索語 |

`title_excluded=1`はタイトル除外、`domain_eligible=0`は分野外・未判定。`matched_domains`にはAI／IoTの配列を保存する。タイトル理由は`title_exclusion_terms`、判定版は`title_filter_policy`と`domain_filter_policy`に保存する。

既存DBも再判定する。旧方針の除外理由を更新し、検索対象だった一般記事を分野外へ変更する。以前保存した原文は確認用に保持するが、読込み・検索・集計から外す。

対象の記事読込み、対象件数、候補語の検索・一致詳細のすべてに次の条件を適用する。

- title_excludedが0、かつ現在のタイトル除外関数でも除外語に一致しない。
- 同じ記事IDのタイトル除外記録がない。
- domain_eligibleが1、かつdomain_filter_policyが現在版。

検索のSQLでは`eligible_articles AS MATERIALIZED`を先に作り、その対象だけを候補語と結合する。除外記事の本文を候補語の検索関数へ渡してから結果を捨てる方式にはしない。

JSONインポートでも同じ条件を適用する。タイトルで除外する記事は本文を記事モデルへ読込み・検証する前に省く。タイトルを通過してもAI／IoT条件を満たさない記事は、本文をterm_articlesへ保存しない。JSONファイル自体の構文解析は行う。

## 候補語検索とカウント

labelとaliasesをORで検索し、タイトル・本文のどちらかで一致すれば受理する。NFKC正規化・casefold・英数字境界を使用し、日本語は複合語内の部分一致を許可する。definition・reasonは検索文字列に使用しない。分野は前段で制限するため、語彙のdomain_termsによる追加の候補検索条件は使用しない。

一致候補数は`COUNT(DISTINCT concept_id)`。同じ候補の繰り返しや複数aliasesの一致は1候補。一致語数は`COUNT(DISTINCT term)`で別に記録する。例えば監視とモニタリングの両方があれば、一致候補数1・一致語数2。候補のhigh／normal・originによる検索除外は行わない。一致ゼロを含む全対象記事を表へ出し、候補数降順・記事ID順で並べる。

## CLIと出力

```powershell
news-weave extraction import --database <corpus.sqlite> --corpus <corpus_id> --domain-label "AI・IoT製品・サービス" --articles <articles.json>
news-weave extraction count --database <corpus.sqlite> --corpus <corpus_id> --vocabulary <vocabulary.json> --output <directory>
```

記事JSONはarticle_id・title・bodyを持つ配列で、urlを任意で保存する。記事IDがない場合はurl、次いでitem_idを使用する。同一入力内のID重複はエラー。countは先に記事を保存したDBを必須とし、最低対象件数は既定200。小規模テストなどで最低件数を明示する機能は残すが、今回の実記事実行では件数条件を緩和しない。

| 出力 | 内容 |
| --- | --- |
| counts.md / counts.csv | 記事・分野・一致候補数・一致語数・含んでいる語の表 |
| counts.json | 候補IDと一致語、各記事の分野と判定語、保存件数・除外件数・方針版・語彙ハッシュ |
| excluded-articles.json / excluded-articles.csv | 除外記事と理由。title_keywordとoutside_ai_iotを区別 |
| domain-screenings.json | 分野判定の記録 |

新規除外記事の本文を保存しないため、保存済み本文件数と、タイトル等を判定した記事件数は区別する。

## 2026-10-13：商品サービス限定と1,000記事の埋め込み

追加の8語は保存済み記事にも適用する。商品サービス限定のコーパスでは、require_product_service=1を保存し、公式種類の確認結果をterm_release_type_screeningsに記録する。release_type_excluded=1の記事は記事読み出し・件数・SQL候補検索のすべてから除く。種類未確認も対象外とする。既存の本文は監査用に保持する。

PR TIMESの公開キーワード検索では種類指定を併用できず、ユーザーの明示選択により、公開AI／IoT検索で候補を取得し、各記事の公式種類が商品サービスであることを確認して採用する。メディアユーザー向け詳細検索にはログインが必要だが、今回そのアカウントは使用しない。タイトルから種類を推測しない。

候補数による足切りを維持し、一致候補数5以上が1,000件になるまで追加する。埋め込み計算はその1,000記事だけが対象であり、足切り前の記事を1,000件集めるだけでは完了としない。既存の本文・モデル・表現方式が同じベクトルを再利用し、未計算区間だけtext-embedding-3-smallへ送る。成功応答のusageを累計し、公式単価$0.02/100万入力トークンから今回の合計と記事当たり平均を推定する。UMAPとHDBSCANのローカル計算には追加のOpenAI API料金は発生しない。
