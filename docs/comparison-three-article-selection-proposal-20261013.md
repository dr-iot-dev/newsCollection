# クラスタ内から比較に適した3記事を選ぶ方法・手順の提案

作成・更新日：2026-10-13。状態：設計提案。手順2をLLMによる自動化案へ更新した。この記事選択は未実装・未実行。以下の重み・閾値は評価用の初期値であり、実記事での評価後に確定する。

## 1. 推奨する方法と目的

**LLMで記事を構造化して比較する用途を揃え、全3ペアの比較適否を判定し、メドイドを基準に類似度の下限を満たす3記事の組合せをMMRで評価する。共通の比較項目と違いはルールで確認する。**

選びたいのは、読者が同じ目的で選択肢として検討でき、共通の項目で違いを説明できる3記事。各記事の代表性、3記事間の共通性、製品・サービスの違い、記載情報の充実度を評価する。

Extractionの既存の候補語カウントを入力条件として使用する。比較対象・比較項目の確認は、その後の比較記事選定の工程として設ける。価格などの記事にない値を補って比較項目を埋めない。

## 3. 考えられる方法と採用方針

| 方法 | 手順 | 今回の使い方 |
| --- | --- | --- |
| 重心上位3件 | 重心とのコサイン類似度順に3件選ぶ | 比較評価の基準方式として使う |
| メドイド＋近傍2件 | 他の記事との平均類似度が最大の記事を選び、近い2件を追加する | 共通テーマを揃える基準方式として使う |
| 最低ペア類似度の最大化 | 3ペアのうち最低の類似度が最大になる組合せを選ぶ | 1件だけテーマが離れることを抑える基準方式として使う |
| MMR | テーマへの関連性を評価し、選択済み記事との重複を減点する | 推奨方式の組合せ評価に使う |
| 比較項目の充実度 | 3件で共通して説明できる項目と違いを確認する | 最終採用条件として使う |

MMRは関連性と冗長性を調整する考え方。[Jaime CarbonellによるMMRの解説](https://www.cs.cmu.edu/afs/cs.cmu.edu/academic/class/15381-s01/public/www/lec/ir/jgc-ir-handout.pdf)を参照する。以下はその考え方を今回のデータに合わせた設計であり、記載する重みや合否基準は本提案独自の初期値。

HDBSCANの帰属確率は所属の強さを表す。[公式APIの定義](https://hdbscan.readthedocs.io/en/latest/api.html)に従い、比較内容の正解率としては扱わない。

## 4. 具体的な実行手順

### 手順1：入力を固定し、クラスタ別の候補表を作る

1. 入力ファイルのSHA-256、クラスタ解析のrun_key、選定方針の版を記録する。
2. クラスタIDごとに所属記事を集める。F ID・組織IDは元の番号を保持する。
3. 組織の重複、候補数5未満、本文入力ハッシュの不一致があれば入力エラーとして止める。
4. 全所属記事について、タイトル、組織、公開日時、帰属確率、現在のコア判定を表示する。
5. 保存ベクトルをL2正規化し、クラスタ内の全ペアのコサイン類似度を計算・保存する。

```text
s(i,j) = 正規化済み元ベクトル vi と vj の内積
u(i,j) = (s(i,j) + 1) / 2
```

sは-1〜1、uは0〜1。類似度の下限判定にはs、後述の加重スコアにはuを使う。

### 手順2：LLMで同じ目的の比較候補を自動で揃える

**記事ごとの構造化 → 表記・比較対象の統一 → ペア判定 → 全3ペアのルール検証**を標準処理とする。通常の選定は自動で進め、人の確認は精度評価用のサンプルと保留案件に絞る。

#### 2-1. 保存済み本文から記事プロフィールを作る

クラスタ所属の327記事について、保存済みタイトル・本文全体をLLMへ入力し、次の情報をJSONで取得する。記事の入力ハッシュごとに1回処理して保存する。

| 記録項目 | 内容・判定例 |
| --- | --- |
| comparison_target | 比較する製品・サービス名、記載されている提供元・型番・版。対象を特定できなければ不明 |
| purpose | 解決する課題・用途。例：住宅内のインターネット接続 |
| audience | 利用者・利用場面。例：家庭利用、製造現場、法人の問い合わせ窓口 |
| category | 比較する製品・サービスの範囲。例：家庭向けWi-Fiルーター |
| comparison_group | 正規化した用途・利用者・カテゴリをもとに後段で付与する仮のグループID |
| axis_values | 記載されている比較項目と値。記載なしは不明 |
| screening_reason | 対象を特定した理由、不明とした理由などの短い判定説明 |
| status | ready／unknown／multiple_targetsなどの処理状態 |

記載のない値はnullまたは空配列とする。1記事に複数の製品・サービスがある場合は個別に記録し、今回比較する対象を明示する。対象を絞れない記事はunknownとして保留する。用途や利用者が複数ある場合も保持し、比較する共通の用途を後段で特定する。

JSONの項目・型・判定値は、OpenAI APIのStructured Outputsで固定する。[OpenAI公式ドキュメント](https://developers.openai.com/api/docs/guides/structured-outputs)によるとスキーマへの適合を制御できるが、内容の誤りは残り得る。APIの拒否・出力途中終了は判定結果と分けて記録し、正常な判定として採用しない。

#### 2-2. 表記と比較対象を統一する

「家庭用」「住宅向け」などの表記を、用途・利用者・カテゴリの正規化辞書にまとめる。初回はクラスタ内のプロフィールからLLMに辞書案を作らせ、対応関係・辞書の版を保存する。意味が曖昧な語を強制的に同じ分類へ入れず、不明として保持する。

例えば家庭向けルーターと産業向け通信ゲートウェイが同じクラスタにあっても、用途・利用者を分けて仮の比較グループを作る。グループIDは正規化辞書と共通用途からプログラムで付与し、記事ごとにLLMが生成した自由なグループ名をそのまま識別子にしない。

同じ共同発表を別組織が配信している場合などは、製品名・提供元・型番・版の記載と後述のsame_target判定を使って重複候補を確認する。同一対象と確定できた記事は1つにまとめ、比較項目の記載数が多いもの、同数なら公開日時の新しいもの、その後F ID昇順で残す。名称が似ているだけの対象や、同一性が不明な対象は自動で統合しない。

#### 2-3. クラスタ内の各記事ペアをLLMで判定する

同じクラスタの全ペアに対して、まず保存済みプロフィールを渡す。確認するペアは最大1,969組で、重複記事の整理後は減る。仮グループの一致だけで比較可能と確定せず、異なる仮グループ間にも必要なペア判定を行い、分類の表記差による見落としを確認する。

| ペア判定項目 | 出力 |
| --- | --- |
| same_target | 同じ製品・サービスか：yes／no／unknown |
| comparable | 同じ目的の選択肢として比較できるか：yes／no／unknown |
| shared_purpose | 2記事で比較する共通用途。判定できなければnull |
| shared_axes | 比較できる共通項目と、単位・対象条件等を揃えられるか |
| reason | 判定の短い理由 |

プロフィールだけでは判定できない場合に限り、保存済み本文の必要な箇所を追加し、再判定する。不足が残れば本文全体を参照できるが、追加判定は最大1回とする。判定不明はunknownのまま保存する。LLMが申告した確信度を、正解率や自動採用の閾値として使わない。

記事AとBを入れ替えて同じ結果を再利用できるよう、ペアIDはF IDの昇順で固定する。キャッシュキーには2記事のプロフィールのハッシュ、モデルの固定版、スキーマ・プロンプト・正規化辞書の版を含める。本文を追加した場合は追加入力のハッシュも記録する。モデルや判定方針が変わった結果を同じキャッシュとして扱わない。

#### 2-4. 3記事すべての比較適否をプログラムで検証する

ペア判定から、comparable=yesかつsame_target=noのペアを比較可能な辺として保存する。3記事を候補にするには、A–B、A–C、B–Cの全3ペアがこの条件を満たす必要がある。

A–BとB–Cが比較可能でもA–Cが比較可能とは限らない。ペアの連結だけで比較グループを確定せず、3ペアすべてを検証する。また、3ペアのshared_purposeが同じ用途に対応することを確認する。対応が不明ならneeds_reviewとする。

1クラスタに複数の仮の比較グループがある場合は、3件以上を持つグループから1組を選ぶ。優先順は候補記事数の降順、同数なら平均ペア類似度の降順、その後グループID昇順。仮グループ間で共通用途が確認された候補は正規化辞書へ対応関係を反映して再編成し、ペア判定をキャッシュから参照する。優先グループで成立する組合せがなければ次のグループを調べる。

全3ペアが通過した候補について、共通の比較項目と違いを手順6のルールで検証し、メドイド・MMRによる選択へ渡す。用途・対象・項目の判定が不明な候補は、後段の高い類似度やスコアだけで自動採用しない。

人の確認は、調整用・評価用の固定サンプルと、必要に応じたneeds_review案件に限定する。保留案件の人による確認は通常の自動処理を止めず、確認済みの修正は元のLLM判定と区別して保存する。

### 手順3：比較グループのメドイドを求める

比較グループGの各記事について、他の記事との平均コサイン類似度を計算する。

```text
centrality(i) = sum(s(i,j), j in G and j != i) / (記事数 - 1)
m = centralityが最大の記事
```

mを基準記事（メドイド）とする。距離を1-sと定義したとき、他の記事への距離の合計が最小になる実際の記事。平均値が同じなら帰属確率降順、公開日時降順、F ID昇順で選ぶ。

クラスタ全体の重心上位記事と、比較グループ内のメドイドは一致しない場合がある。用途を揃えた比較グループ内で基準記事を求める。

### 手順4：基準記事と他の記事が一緒に分類される安定度を求める

保存済みの6通りの条件変更結果から、記事iと基準記事mが同じ非ノイズクラスタになる割合を計算する。

```text
A(i,m) = 同じ非ノイズクラスタになった回数 / 6
```

両方がノイズの回は同クラスタとして数えない。記事iが何らかのクラスタに入った割合と、mと同じクラスタになった割合を区別する。6通りの結果が欠けていれば安定度は不明とし、標準スコアを確定する前に不足データを補う。

### 手順5：基準記事を含む3記事の組合せを評価する

帰属確率p、基準記事との近さ、同クラスタになる安定度から関連性Rを求める。

```text
R(i) = 0.70 * u(i,m) + 0.15 * p(i) + 0.15 * A(i,m)
MMR(i | S) = 0.75 * R(i) - 0.25 * max(u(i,j), j in S)
```

MMRの関連性側の重み0.75は初期値。帰属確率が同点でも、元空間の類似度と安定度で評価できる。

1. mを含む3記事の全組合せ {m,b,c} を列挙する。
2. 次の条件をすべて満たす組合せだけを残す。
   - 3件が同じcomparison_groupに入っている。
   - 全3ペアがcomparable=yesかつsame_target=noであり、共通の比較用途が確認できる。
   - 3組織、3つの異なる比較対象の製品・サービスである。
   - 3ペアすべてで元空間の類似度sが下限τ以上。
   - 後述の共通比較項目と差異の条件を満たす。
3. b→cとc→bの両方の順序でMMRを計算し、大きい方を組合せスコアとする。

```text
T(m,b,c) = max(
  MMR(b | {m}) + MMR(c | {m,b}),
  MMR(c | {m}) + MMR(b | {m,c})
)
```

4. Tが最大の組合せを採用候補とする。同点は最低ペア類似度降順、平均ペア類似度降順、昇順に並べたF IDの辞書順で決定する。浮動小数の同点許容差は1e-12とする。
5. mを含む成立する組合せがなければ、centrality順で次の基準記事を試す。最初に成立した基準記事で最良の組合せを選ぶ。
6. どの基準記事でも成立しなければ、次の比較グループへ進む。全グループで成立しなければ、そのクラスタを保留にする。

現在の最大クラスタは26記事なので、基準記事を固定すると最大300通りの相手2記事の組合せがある。基準記事を変える場合も類似度・比較条件はキャッシュする。全30クラスタの重複しない3記事の組合せは8,836通りであり、全組合せによる基準方式との比較も可能。

### 手順6：共通の比較項目と違いを自動検証する

初期の比較項目は、機能、処理方式、対応環境、利用・提供形態、提供条件、価格・費用の6種類とする。カテゴリに合わせて項目名を具体化する。例えばルーターなら通信規格・接続方式・設置環境・管理方式などを使う。

採用条件の初期案は次の2つ。

- **少なくとも2項目**について、3記事すべてに比較できる記載がある。
- **少なくとも1項目**について、2種類以上の意味のある違いを説明できる。

単なる製品名・企業名・宣伝文句の違いは差異として数えない。同じ項目でも対象条件や単位が違う数値は、条件を揃えて比較できるか確認する。公開されていない価格は不明として表示し、その項目を共通項目数に含めない。

手順2のaxis_valuesとshared_axesを使用し、項目ID・単位・対象条件が対応する値の共通部分をプログラムで数える。価格の税込／税別や一時費用／月額費用など、比較条件が揃わない値は同じ項目として数えない。差異は正規化した値・機能集合等から求め、意味のある違いか不明な場合だけLLMに判定させ、未確定なら保留する。

最終表では、選定した3記事の共通目的、比較項目、違いを短文で確認できるようにする。判定不明の組合せはneeds_reviewとして残す。

## 5. 初期パラメータと調整方法

| パラメータ | 初期案 | 位置づけ |
| --- | ---: | --- |
| 最低ペア類似度τ | 0.55 | 実記事で調整する仮の下限 |
| MMR関連性側の重み | 0.75 | 関連性を優先しつつ重複を減点 |
| Rの元空間類似度の重み | 0.70 | 比較テーマへの近さを主指標にする |
| Rの帰属確率／安定度の重み | 各0.15 | 補助指標として使用 |
| 共通して比較できる項目 | 2以上 | 初期の採用条件 |
| 違いを説明できる項目 | 1以上 | 初期の採用条件 |

0.55を普遍的な比較可能性の境界とは解釈しない。本文全体の埋め込みなので、会社説明や記事構成の共通性も類似度に影響する。

調整は次の順で行う。

1. 30クラスタから10クラスタを、記事数・平均ペア類似度・コア件数が偏らないように選び、調整用として固定する。残り20クラスタは評価用に残す。
   手順2の精度評価用には、用途が揃うペア、用途が離れるペア、共同発表等の同一対象、複数製品を含む記事、不明な記載を含む固定サンプルを選び、人が正解・保留の基準を付ける。全327記事への人の判定付与は必須にしない。
2. 調整用でτ=0.50／0.55／0.60／0.65、MMR重み=0.65／0.75／0.85を試す。Rの重みは初回は固定する。
3. 各設定の採用件数とサンプルの本文確認結果を並べる。構造化項目の誤り、ペアの誤採用・誤除外、unknown率も確認する。比較可能な組合せの割合を優先し、同程度なら成立するクラスタ数の多い設定を選ぶ。
4. パラメータを固定し、評価用20クラスタに適用する。評価用の結果を見て同じデータに合わせて調整し続けない。
5. 設定、判定者、調整用／評価用のクラスタID、合否理由を保存する。データを増やして再調整する場合は方針版を更新する。

全クラスタで3件を揃えるために、自動でτや本文の採用条件を緩める処理は初回には設けない。比較が成立しない理由を見て、用途グループの確認や追加収集の必要性を判断する。

## 6. 保留と採用の状態

| 状態 | 意味 |
| --- | --- |
| selected | 3記事が全ペア判定・類似度・比較項目の自動採用条件を満たす |
| needs_review | 用途・比較対象・比較項目の判定が未確定 |
| processing_failed | API失敗・拒否・出力途中終了等で判定を取得できない |
| insufficient_comparable_articles | 同じ比較グループの異なる対象が3件未満 |
| incompatible_article_pair | 全3ペアが比較可能な組合せがない |
| similarity_below_threshold | 3ペアすべてがτを満たす組合せがない |
| insufficient_comparison_axes | 共通2項目以上の記載が揃わない |
| no_meaningful_difference | 比較に使える違いを説明できない |

候補数と各段階の失敗数を記録し、複数理由がある場合は理由の配列も保存する。条件を満たす組合せがあればselectedを優先する。成立する組合せがない場合は、結果を変え得る未完了処理をprocessing_failed、判定不明をneeds_reviewとして扱い、それ以外は最初に未達になった選定条件を代表状態にする。成立しないクラスタには2件を「3記事選定済み」として出さない。

## 8. 評価・実装の順序

1. 保存データの読込み、組織一意性、入力ハッシュ、元空間の類似度の検証を実装する。
2. 327記事の構造化、正規化辞書、最大1,969ペアの自動判定・キャッシュ・保留処理を実装する。APIのバッチ化によって通信回数は変わるため、記事数・ペア数とAPI要求数を区別して記録する。
   固定サンプルに人の基準判定を付け、手順2の自動判定を評価する。通常の選定は人の確認待ちにせず、判定不明な候補を保留して先へ進める。
3. 重心上位3件、メドイド＋近傍2件、最低ペア類似度最大化の3方式を基準結果として生成する。いずれも同じ用途・対象・比較項目の条件で評価する。
4. 本提案のMMR組合せ評価を実装し、調整用10クラスタで初期パラメータを比較する。
5. 固定した設定で評価用20クラスタを評価し、採用・保留の表を保存する。

評価項目は、3記事が同じ目的で比較できるか、別の製品・サービスであるか、共通の比較項目と違いを説明できるか、成立するクラスタ数、元空間の最低類似度、選定理由を再現できるか。基準方式と本提案を同じ基準で確認する。

実装時の検証には、ノイズが混入しないこと、3組織・3対象の一意性、全3ペアの比較可能判定、基準記事と3ペアの類似度下限、同点時の決定、成立する3件目がない組合せの拒否、保留理由を含める。A–B・B–Cだけが比較可能な組合せを拒否すること、API失敗と判定不明の区別、再開時のキャッシュ再利用も確認する。固定したLLM判定・辞書の入力順を変えても同じ選定結果になることを検証し、新しいLLM呼び出しの判定変動は別に測定する。

ベクトル計算とMMR・組合せ評価は保存済みデータを使うローカル処理。新たな埋め込みAPI料金は発生しない。手順2の構造化・正規化・ペア判定にはLLM処理料金が発生する。実装前に対応モデルの固定版を選び、工程ごとの入力・出力トークン実使用量とそのモデルの単価から推定する。モデル名・単価・具体的な料金はこの設計更新では未確定。今回実施したのは提案ファイルの更新のみで、LLMへの記事送信は実行していない。
