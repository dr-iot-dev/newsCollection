# 比較記事生成・不適記録・採点方式選定の評価計画

更新日：2026-10-14。ユーザーの訂正により、今回の検証は完成した比較記事1本ずつ行う。現在の指示は[A案の理解と修正した検証指示](comparison-A-instructions-20261014.md)を参照する。以下の全記事一括採点を今回の検証にも必要と解釈したことは誤りであり、一括入力・全セル・全段落・全ペア・12項目の必須出力を追加した契約は現行の検証に使わない。v7の3件という結果は修正後のAの確定結果ではない。修正指示の個別評価は[全30クラスターの個別評価結果](comparison-A-individual-all30-results-20261014.md)を参照。実WordPress投稿は未実施。以下の過去の実験計画・実測は履歴として保持する。

## 1. 今回の方針

主目的は、問題のない比較記事をいくつか作成すること。最適な比較記事の本数や全クラスタの採用率を最大化しない。少数の取りこぼしは許容し、不適・未確認の記事を採用しないことを優先する。採用0本を成功とは扱わないが、本数を確保するために採否条件を緩めない。

- 埋め込みとクラスタリングまでの処理は継続する。
- 初期の3記事選定は既存ベクトルによるMMRなどで簡単に行う。クラスタ全記事のLLM構造化や全ペア適否判定は標準工程に戻さない。
- 生成モデルは生成時にも、3者が別対象か、共通の判断目的があるか、原資料にない説明を加えていないかを明示的に点検する。不具合を検出したら「比較不適」と理由・根拠を残す。
- 評価・検証には生成モデルと異なるモデルを用い、同じ3項目を原資料に照らして再検証する。別モデルによって生成側の見落としや誤判断を追加検出することが目的であり、確認項目を生成側と評価側に振り分ける設計にはしない。
- 選び直しはクラスタごとに最大1回。初回と合わせて最大2組を試し、2組目も適切でなければ却下する。
- 採点A「全記事の一括採点」と採点B「個別採点後に全体の重複・採点整合を確認」を構築時に比較する。本番では選定した一方だけを使う。両方式の恒常実行や点数平均は行わない。

## 2. 生成時の不適記録を後段で処理する方式の評価

生成時と評価時の両方で、比較の成立条件と原資料への忠実さを明示的に点検する。生成時の確認を省き、後段で初めて確認する設計にはしない。

### 生成・検証に共通の必須確認項目

|確認項目|生成モデルの処理|別の評価モデルの処理|
|---|---|---|
|3者は別の比較対象か|原資料の製品名・提供元・型番・共同発表情報を照合し、同じ対象を別製品として並べない|同じ原資料に照らして別対象であるかを再判定し、生成側の誤認を確認する|
|共通の判断目的があるか|誰が何を決めるための比較かを具体化し、成立しなければ不適とする|本文がその判断に役立つか、用途や対象を無理にまとめていないか再判定する|
|原資料にない説明を加えていないか|機能・条件・数値・解釈の根拠を確認し、裏付けのない説明を加えない|本文と原文を照合し、根拠のない追加や条件の取り違えを検出する|

各項目の判定と原文根拠を記録し、問題があれば生成時から不適と明示する。完成記事同士の内容重複は、全体の評価段階で追加確認する。

### 別モデルによる検証の目的

追加検証の主目的は、生成モデルが同じ項目を確認した後にも残る、モデルによる見落とし・解釈違いを別モデルで検出することにある。評価側だけに確認項目を持たせることや、同じモデルに別プロンプトで再点検させることを、この別モデル検証の代わりとは扱わない。

評価モデルには生成モデルの「適切」という結論を正解として渡さず、原資料と完成記事から自身の判定と根拠を出させる。生成側で不適としたものは従来どおり除外へ反映する。採用判定に必要な原文を評価側が読めるようにし、生成側の要約だけに依存しない。

原資料を生成モデルと評価モデルが共通に読むことは必要である。生成側が原文の一部を取り落としていた場合にも確認できるよう、原資料そのものを参照できる形を保つ。完成文だけで省略された事実まで確認できると期待しない。

別モデルでも同じ誤りをする可能性はあるため、誤りの確率が独立であるとは仮定しない。改善量は未測定であり、既知の不適例を使い、生成側が見逃し、別モデルが追加検出し、その指摘を原文で確認できた件数を記録する。これは少数の問題のない記事を採用するための検証であり、疑義が解消しない記事の救済は必須としない。

不適の記録は、本文中の曖昧な注意書きだけにしない。人が読める表示と、プログラムで扱える状態を同じ生成結果に保持する。例えば次の形を用いる。

|項目|内容|
|---|---|
|comparison_status|eligible / ineligible / needs_confirmation|
|generation_checks|生成モデルによる共通3項目の判定と原文根拠|
|issues|理由コード、該当する記事ID、短い説明、原資料の該当箇所|
|source_article_ids|選んだ3記事のID・URL・入力ハッシュ|
|attempt|初回0、選び直し後1|
|article_markdown|比較本文、または「比較不適（公開不可）」と理由を示す記録|

理由コードの例はsame_target、no_common_decision、insufficient_evidence、duplicate_comparison。名前の似通いだけでsame_targetを断定せず、共同発表・同じ型番等の根拠を示す。「疑い」と「確定した不具合」は分ける。

後段の扱いは次のとおり。

1. ineligibleは不適として記録し、公開・通常順位の対象から外す。参考品質点を付けても採否は覆さない。通常順位用の点数はnullとし、0点の記事と混ぜない。
2. needs_confirmationは疑義を確認してから採否を決める。未解決のまま適切として通さない。少数の取りこぼしは許容するため、難しい疑義の救済は必須とせず、選び直し枠があっても解決費用をかけず却下してよい。従来の抽出unknownを一律不適にする規則は復活させず、完成記事に関する具体的な疑義と根拠不足を記録する。
3. eligibleも、後段で本文の矛盾や完成記事間の内容重複が見つかれば不適にできる。評価結果に問題箇所を残す。
4. 不適表示・理由・記事IDは、Markdown化、要約、保存、採点入力への引き渡しで失わない。正常な生成結果として必要項目が欠けたものは技術的な処理失敗として扱い、適切な記事とは扱わない。
5. 明らかな不適であれば、無理に完成した比較本文を作る必要はない。不適結果を出すことを正常な生成結果として認める。

PR TIMESの配信IDは引き続き統合せず、各IDの最新記事を選ぶ。その後に同じ製品・共同発表を比較対象として重ねないよう扱い、配信IDと来歴はそのまま保持する。

## 3. 選び直しは1回でよいか

費用と複雑さを抑える運用上の方針として妥当である。少数の問題のない記事を得る目的なので、初回で最適な3記事を完全に探すことに費用をかけない。明確で簡単に反映できる不適理由なら最大1回選び直すが、全ての不適クラスタを救済することは必須としない。

ただし、2組目の却下は「このクラスタには比較可能な組が一切ない」という証明ではない。「設定された試行回数内で採用に至らなかった」という運用上の結論として記録する。

|状態|次の処理|
|---|---|
|初回が適切|採点・重複整理へ進む|
|初回が不適で代替組がある|理由を反映して、別の3記事組を1回だけ選ぶ|
|初回が不適で代替組がない|却下|
|選び直し後が適切|採点・重複整理へ進む|
|選び直し後も不適、または未解決|却下。3組目は試さない|

同じ3記事を並べ替えただけのものは別組としない。共同発表の重複なら、問題の2記事を同じ組に入れないという制約だけ加えて選び直す。一方の元記事をクラスタ全体から永久に除外する必要はない。完成記事同士の内容重複が後段で判明した場合も、選び直し枠を新たに追加せず、同じ最大1回の枠を使う。

API通信失敗などの技術的な再試行は別に記録して上限を設ける。品質改善を名目に同じ組で無制限に生成し続ける処理も設けない。

過去の評価は、厳しい初期の適否判定で落ちた組にも有用な比較があったことを示している。一方、単純選定と複雑選定を同条件で比較した実験ではなく、「複雑な選定は常に効果がない」とまでは確定していない。現段階では簡単な選定を標準にし、初回採用率、選び直しによる救済率、却下率、採用1本当たり費用を記録する方針が合理的である。

## 4. 採点AとBの比較は構築時だけ行う

Aの方が不安定だと先に決めない。全体の相対関係を見やすいAと、個別の根拠を確認しやすいBを、同じ記事で比較して本番方式を選ぶ。

|条件|採点A：全記事の一括採点|採点B：個別採点＋全体確認|
|---|---|---|
|採点入力|全ての完成記事と共通メタ情報を1リクエストへ渡す|同じ完成記事とメタ情報を1記事ずつ独立リクエストへ渡す|
|共通基準|同じ100点ルーブリック、同じ採否条件|左と同じ|
|全体で行う処理|その1リクエスト内で内容重複・全体整合も判断|個別点と理由を保存した後、全体の重複・採点整合を別リクエストで確認|
|最終出力|採否、軸別点、根拠、重複群、代表記事|同じ出力に加え、調整前後の点数と調整理由|
|本番採用時|Aだけ実行|Bの個別採点と全体確認だけ実行|

Bの2段階目はBという一つの方式を構成する工程であり、本番でAも併用する意味ではない。採点方式間で平均・合議して最終点を作らない。

### 4-1. 入力と評価条件を固定する

- 主比較では、保存済み実生成の適否マーク・理由・確認記録を保持する。今回の14組は共通規則で7組を除外し、残る7記事を同じハッシュでA/Bに渡す。新方式の生成記録を持たない旧20本は今回の方式選定の根拠から外し、履歴として保存する。生成結果を採点方式ごとに別々に作らない。
- 元順位、MMR値、以前の品質点は採点入力に入れない。記事は無作為な識別子で提示する。
- AとBには同じ評価モデル版・設定、同じルーブリック、同じ不適判定条件を使う。この評価モデルは生成モデルと異なるものに固定する。生成モデルを変更した場合は評価モデルとの組合せも記録する。出力の必要量を確保し、Aが全件の理由を出せないほど小さな出力上限は設けない。
- 記事本文、生成時の不適記録、比較対象・原記事ID、共通の根拠情報は両方式に同じものを渡す。原資料の事実検証は共通工程として固定し、採点方式だけの差と混ぜない。
- Bの全体確認では、最初の公平比較は全記事本文にもアクセスできる条件にする。要約だけへ減らす最適化は別条件として測り、その情報量の差を採点方式の差と混同しない。
- Aの入力が収まらなければ本文を黙って切り捨てない。その規模での実行不能を記録し、分割する方式を試すならAとは別条件とする。
- 各方式を探索的に3回試す。提示順を固定した再実行と、順序を変えた実行を含め、採点の再現性と順序変更時の変動を確認する。少数回の実験から精密な信頼性までは主張しない。

### 4-2. 比較する指標

|観点|測るもの|
|---|---|
|品質判断の妥当性|人が原文に基づいて付けた採否・品質評価との一致、上位記事の判断への有用性|
|不適の検出|既知の不適の見逃し、適切なものの誤除外、生成モデルの見逃しを別モデルが正しく追加検出した件数|
|重複整理|同じ比較内容の検出、異なる比較内容の過剰統合、残す代表の妥当性|
|採点の安定性|同じ記事の点数幅、採否の反転、上位集合と順位の変化|
|根拠の質|本文に対応する理由があるか、点数と理由が整合するか|
|実用性|API使用量・料金、呼出数、実時間、欠落・出力途中終了の件数|

AとBの順位が一致しても、両方が誤っている可能性はある。方式間の順位相関だけで優劣を決めない。前回のCodex点数も作成者による既知評価なので、暫定参考とし、独立した正解とは扱わない。

20本は編集・検証済みであり、共同発表の誤比較などの明白な不適を十分に含まない。不適表示が正しく後段へ伝わるか、生成側が表示を付け忘れないかは、既知の共同発表例C07等を含む別の評価例で確認する。自然発生例と、問題箇所が分かるように作った試験例は区別して集計する。今回の主比較は、生成モデルが実際に返した適否マーク・理由を保持した条件に限定する。マークを持たない人工複製は今回の方式選定の根拠に使わない。生成側の見落としを対象にする別評価を行う場合は、この条件の比較と分ける。

### 4-3. 本番で一方に決める基準

まず採用記事に重大な不適が混入しないことと、根拠のない採用を避けることを優先する。少数の正常記事の取りこぼしは許容し、採用本数や救済率の最大化では方式を選ばない。採用群の問題混入率（問題がある採用記事数／確認した採用記事数）と件数、既知の不適例の通過件数を主指標とする。これらが同程度なら、採用記事の質・採否の安定性、料金・時間・構成の簡潔さで選ぶ。採用本数と誤除外も併記し、全件却下で見かけ上良い結果になることを防ぐ。有限の評価例で問題が0件でも、問題が今後一切発生しない保証とは扱わない。

許容する誤除外率や点数変動幅は、結果を見る前に評価例と運用目的に合わせて固定する。現時点では根拠のない数値閾値を置かない。調整に使った20本だけで採用方式を確定せず、未使用記事でも確認する。

採用後の通常実行は一方のみ。もう一方は構築時の評価結果として保存する。方式変更の検証を改めて行う際を除き、常時比較運用しない。

## 5. 費用と上限の整理

前回の約$2.3／30クラスタは、単一方式の想定工程と、同じ3記事で6本修正する例の試算である。今回のA・B比較実験や、3記事を選び直して事実整理から生成し直す費用はそのままでは含まれない。過去の使用量・試算JSONは履歴として保持し、新方針の実績とは扱わない。

比較実験では本文生成を共用するので、生成費用をA・Bごとに二重計上しない。共通の事実検証と、方式別の採点・全体確認・反復分を分けて記録する。

採点だけの呼出数は、N記事、各方式3回の探索試行なら、Aが3回、Bが3×(N+1)回、計3×(N+2)回。20記事なら66回、30記事なら96回である。これは呼出数であり、Aは入力・出力が大きいので料金比を表さない。実際の入力と出力のトークン数から計算する。

本番の3記事組はクラスタごとに最大2組。Cクラスタなら生成対象組数は最大2Cで、30クラスタなら最大60組。これは修正や検証等を含む全API呼出数が60回という意味ではない。構築時の両方式比較費用を、本番で毎回発生する費用にはしない。

## 7. 現在の個別記事検証の指示

ユーザーの訂正に従い、完成した比較記事1本と原資料・生成時記録を渡し、その記事全体の適否と具体的な理由を1回で判断する。別の完成記事の入力や記事間のペア判定を必要としない。現在の全文指示と出力範囲は[A案の理解と修正した検証指示](comparison-A-instructions-20261014.md)に記載した。

本書の過去の一括採点Aの定義を、今回の検証にそのまま適用したことは誤りだった。全セル・段落、全記事ペア、12項目の合格を必須出力にしない。機械的な出力不備は処理失敗として内容の不適と区別する。具体的な内容問題・解消不能な重大な疑義は採用しないが、未記載や役割差だけで不適にしない。対象数を過去の実験の7件に固定しない。

WordPress向けv7の要求・応答・記事・下書きファイルは履歴として保存する。指示とJSON契約の不整合、住宅IoTの表の出典割当誤りがあるため、その3件という結果を修正後のAの確定結果として扱わない。現在の個別検証指示とv7の契約は併用しない。その後、ユーザーの依頼により全30クラスターの完成本文28本を1本ずつAPI評価した（初期5件は再利用）。モデルは全件を適切としたが、既知のC07・C08の問題も通過した。WordPress投稿は行っていない。
