# Discovery改善計画：比較対象記事を探す検索語彙

作成日：2026-10-12。状態：計画。Discoveryの目的を、比較対象として適切な記事を一般的な語句検索で探すための語彙生成へ再定義する。

## 目的と現状の問題

入力の3〜5記事は、その分野を把握する種資料とする。出力は、種資料に登場した製品だけでなく、同分野の別製品・別記事にも使える検索概念と同義語。比較表の列・質問・採用件数は別の設計として扱う。

現行実装の候補数が少ない理由：

- 「一般的」を「入力記事の2件以上に出現する」としていた。最終の5記事群ではLLMの20候補を10候補へ削減し、通信方式・対応規格・オフライン動作・ライセンス期間などを除外した。
- 同義語も引用原文に出現することを要求していたため、別記事で使われる表現を追加できなかった。
- GENERIC_SEARCH_FORMSで「データ」などを一律に除外していた。
- 比較表の項目に近い質問と複合語を生成させ、検索語彙の分野全体への展開が不足していた。
- 最大8件制約は既に撤去している。現在の少なさは件数上限ではなく、生成方針と除外条件による。

## 語の粒度と関係

| 現行表現 | 検索概念としての整理案 |
| --- | --- |
| クラウド監視、遠隔監視 | 基本概念「監視」へ統合。実現場所や距離は修飾情報へ移す |
| 遠隔管理 | 基本概念「管理」へ整理 |
| 外部連携 | 基本概念「連携」へ整理 |
| 監視対象データ | 基本概念「データ」へ整理 |

クラウド・遠隔・外部は同義語ではない。修飾された軸を別々に増やすことと、修飾語を同義語にすることは分ける。監視・管理・連携も関連するが意味は異なるため、自動的に同義語へまとめない。近い概念は同じ検索グループに所属させ、独立した検索語として残せるようにする。

軸名は短い一般名詞・名詞句とする。括弧、商品・セット名、長い例示を付けない。「データ」のような広い名詞は採用可能とし、検索時に分野の条件と組み合わせる。

## 同義語の規則

aliasesには、同じ分野・文脈で名称を置き換えても指す概念が変わらない語と、同じ名称の表記違いだけを入れる。入力記事に登場しない一般的な同義語も許可する。確実な同義語がなければ空配列にする。

| 語の組み合わせ | 扱い |
| --- | --- |
| 監視、モニタリング | 文脈上同じ概念を指す場合、同義語 |
| 価格、値段 | 同義語 |
| データ保存、データ保存期間 | 機能と属性。別概念であり同義語にしない |
| 通信、LTE | 上位概念と具体方式。同義語にしない |
| 通知、メール | 機能と手段。同義語にしない |
| 監視、管理、連携 | 関連概念。同義語にしない |

関連語・下位概念・属性・具体値をaliasesに混ぜない。必要なものは、一般性を判断して独立した検索概念へ登録するか、概念間の関係として記録する。例えば「価格」に「見積」を同義語として入れず、見積が有用なら独立概念として扱う。

同義語であることと、文字列の部分一致で検索にヒットすることも別。複合語中の「データ」に検索が一致しても、その複合語をデータの同義語として登録したことにはしない。

## 新しいDiscoveryの工程

1. **種資料から候補を広く拾う。** 記事別に機能・仕様・技術・利用条件を列挙し、その和集合を取る。1記事だけの記載も保持し、この段階で群内頻度による削除をしない。
2. **基本概念へ正規化する。** 不要な修飾を外し、同じ概念の名称を統合する。「監視」と「管理」のような関連概念は区別する。商品固有の名称・セット別の価格内訳を一般的な名称へ整理する。
3. **分野の語彙を補完する。** 種資料から分野を把握し、同分野の別製品を探す際に使える一般的な機能・仕様・運用・契約の概念を補う。入力5記事に出現することは要求しない。
4. **同義語・表記違いを整える。** 概念の意味を短く定義し、その定義を保つ名称だけをaliasesにする。近い語・手段・具体値は別の関係として扱う。
5. **検索語彙として出力する。** 候補一覧と生成由来を保存する。入力記事内の出現数は参考情報として記録し、採用・削除の条件にしない。

分野補完では、入力・前提、処理・方式、出力・提供、経済・運用の4層を探索と優先順位付けの中心にする。各軸に主となる層と優先理由を記録し、4層の中心的な内容に該当する軸へ重きを置く。層ごとの件数ノルマは設けない。別モデルへ渡す入出力・プロンプトは[Discovery仕様](discovery-search-vocabulary-spec-20261012.md)を参照。

初回評価では30〜50程度の基本概念を得ることを目安にする。これは上限・最低数・スキーマ制約ではない。少なければ、見落とした分野の観点がないかを確認する。修飾違いや類似語を独立軸にして数を増やさない。

IoTでの粒度例：データ、計測、収集、保存、分析、可視化、通信、接続、規格、互換性、監視、検知、通知、制御、管理、連携、自動化、識別、認証、暗号化、権限、精度、遅延、容量、消費電力、耐久性、障害、復旧、設置、導入、運用、保守、更新、保証、価格、契約、ライセンス、試用、サポート、拡張性。

この例は語の粒度の説明であり、全分野で固定採用するリストではない。

## 出力契約

比較表用のDynamicAxisとは別に、検索用のSearchVocabulary契約を作る。

| 項目 | 内容 |
| --- | --- |
| domain_terms | 検索対象の分野・製品種類を絞る語。概念のaliasesとは分ける |
| concepts[].id | 安定した概念ID |
| concepts[].label | 短い一般名称 |
| concepts[].definition | 同義語と関連語を区別するための短い意味定義。検索には使わない |
| concepts[].aliases | 真の同義語と同じ名称の表記違い。0件を許可 |
| concepts[].group | 関連概念をまとめる任意の検索グループ |
| concepts[].origin | observed／generalized／domain_expansion |
| concepts[].source_refs | 種資料に由来する場合の参照。分野補完や未出現の同義語には必須にしない |

比較質問、機能の提供状態、値、過半数条件をこの契約に持ち込まない。種資料に出現した概念と、一般性から補完した概念の由来を表示できるようにする。

## 後段の検索

各概念についてlabelとaliasesのORを通常の文字列検索で判定する。現行のNFKC正規化・大小文字統一・英字境界の処理は活用する。

分野条件と概念条件を分け、例えば「分野の語に一致し、検索概念にも一致する」という条件で候補を拾う。広い語は削除せず、分野条件や複数の概念グループの一致で検索結果を絞る。

同じ概念の同義語が複数ヒットしても1概念として数える。関連概念の一致はグループ単位でも集計し、似た語の重複で順位が上がりすぎないようにする。重み・一致数の閾値は外部記事の評価で決め、Discoveryの採用条件には戻さない。

## 実装順序

1. 検索語彙契約と生成由来の保存形式を追加する。比較表用契約と分離し、既存履歴を保持する。
2. 記事別候補の和集合、基本概念化、分野補完、同義語整理のプロンプトを用意する。現行の「2記事以上」「検索語も引用原文必須」という指示を検索用Discoveryから外す。
3. shared_search_candidatesとAXIS_SEARCH_NOT_SHAREDによる候補削除を新経路へ適用しない。「データ」等の一律除外も外す。頻度は参考値へ変更する。
4. true aliasesだけで検索する処理と、分野条件・概念／グループの一致を出力する処理を整える。既存の技術語や属性をaliasesから分離する。
5. 検索語彙の単独CLIと候補一覧ファイルを用意する。比較表用Discoveryとの出力を明示的に区別する。
6. 種資料以外の記事で検索性能を評価し、語彙・同義語・検索条件を調整する。

主な変更対象：app/contracts/comparison_dynamic_axes_v1.py周辺の新契約、app/ai/dynamic_axes_prompts.py、app/core/comparison_dynamic_axes.py、app/orchestration/comparison_dynamic_axes.py、app/dynamic_axes_cli.py。新しい方針・契約版で実行し、現行の検証済みキャッシュを新語彙へ転用しない。

## 評価計画

- 既存5記事は生成用の種資料とし、検索性能の正解集合には使わない。
- 別製品・別記事の同分野候補と、隣接分野・イベント・調査・会社紹介等の非候補を集める。種資料の転載・同一製品の別版は評価集合から除く。
- 初回は同分野候補20〜30件、非候補20〜30件を目安に、人が検索対象としての関連性を付ける。収集源の偏りを避け、調整用と最終確認用を分ける。
- 現行語彙と新語彙を、同じ評価集合・検索条件で比較する。
- 測定するのは検索の再現率・適合率、検索語彙の分野内カバレッジ、同義語の誤混入、修飾違いによる重複、生成呼出数。原文との一致件数や候補語数だけを成功指標にしない。
- データ／監視対象データ、監視／モニタリング、保存／保存期間、通信／LTE、通知／メールを回帰例にする。
- 別の種資料群でも生成し、同じ基本概念が安定して得られるか確認する。全群で同じ語彙件数になることは要求しない。

完了条件は、種資料外の候補記事を拾えること、aliasesに同義語以外を混ぜないこと、修飾だけの重複を減らすこと。記事の値抽出・比較表・生成品質のAI検証はこの評価の対象外とする。
