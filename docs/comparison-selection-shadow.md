# 根拠付き比較選択の実装と並行評価

対象はnewsWeaveのみ。改善計画の段階1の評価成果物と段階2の契約・保存、および段階3・4の並行評価用の土台を追加した。
新基準で自動探索・執筆・送信する本番経路への接続は、この段階では完了として扱わない。
既存WordPress下書き、原稿履歴、newsCollectionの運用は変更しない。

## 追加した機能

- `comparison_selection_v1.py`: 比較目的、3〜5必須質問、製品と複数資料の対応、セル状態、採否、独立5条件、除外基準、入力ハッシュと方針版。
- `core/comparison_selection.py`: 引用範囲と事実参照、別製品の事実混入、条件消失、質問削除の拒否。製品数とURL数を別々に検査し、発表資料の多数票は補助ページと独立に検査。
- `orchestration/comparison_selection.py`: 固定計画、AI候補評価、抽出後の再順位付けと組み合わせ選択、別モデルの独立検証。利用不可や不足では保留。
- `comparison shadow`: 登録済み資料を明示指定して評価するCLI。原稿・送信パッケージを作らない。手動指定も同じ判定を通る。

AIには入力で許可された事実IDだけを選ばせ、引用文・証拠ID・原文範囲はシステムが原記録から結び付ける。
AIの引用転記に依存せず、保存前に同じ原文・値・条件の検査を通す。

既存`module_messages`に計画、候補評価、工程キャッシュ、最終評価を追記する。
既存JSON・履歴を書き換えず、DBスキーマの変更も不要。
AI呼び出しは既存`ai_runs`にモデル、トークン、費用、処理時間、検証失敗を記録する。
CLIでは確定済み工程を逐次commitし、入力・モデル・プロンプト・方針版の一致時だけ再利用する。
比較検証の失敗理由は固定の診断コードと修復指示として保存し、未確認の応答内容をエラーログへ混ぜない。
資料・事実の更新時は新しい計画を作る。改訂前の計画を保持する。
比較目的を定義できない場合と、任意の追加情報だけが不足する場合を区別し、後者で計画を無条件に保留しない。
候補名と元製品名を入力で区別し、採否理由にも候補名を必須とする。根拠IDは説明文ではなく専用配列へ出力させる。

## 実行方法

新しい3モデルの設定は空を既定とし、設定漏れを既存方式で救済しない。
比較計画・評価モデルと比較検証モデルは必ず異なるモデルにする。

```dotenv
AI_COMPARISON_PLANNER_MODEL=<比較計画のモデル>
AI_COMPARISON_ASSESSOR_MODEL=<比較採否のモデル>
AI_COMPARISON_VERIFIER_MODEL=<別の独立検証モデル>
COMPARISON_MIN_PRODUCTS=3
COMPARISON_MAX_EVALUATIONS=8
```

```console
news-weave comparison shadow --item <元資料UUID> --candidate <候補UUID> --candidate <候補UUID> --output /tmp/selection-audit.json
```

このコマンド自体が明示的なshadow評価であり、schedulerを切り替えない。
`COMPARISON_SELECTION_MODE`はlegacyを既定とする。shadow設定は新探索を自動開始するスイッチではない。
環境設定をshadowへ変えた場合はWordPressの全送信操作を拒否し、旧方式へ迂回して送信しない。
このCLIだけの実行では環境設定を変更せず、既存schedulerの運転も切り替えない。
CLI終了コードは適合0、保留2、入力・DBエラー1。出力には計画、採否、事実ID・原文引用、
モデル実行ID、独立検証、保留理由と不足質問、具体項目の比較表を含む。

`--exclusion-baseline`に`SourceExclusionBaselineV1`のJSONを渡すと、元資料と候補のURL・
同一本文hash・同一発表keyを除外する。共通仕様書の例外を設けない。
WordPress・ローカル全履歴を照合した除外基準の収集と、送信直前の並行使用検査は後続工程。
この評価コマンドが既存の除外基準を自動収集したと扱わない。

現在のCLIは1登録発表を1製品に対応させる。契約・充足検査は複数ページを区別するが、
公式補助ページの自動取得・製品への紐付けはまだ接続しない。
外部検索は未設定として探索範囲を保存し、新ホストを自動承認しない。

## 次の実装と導入条件

1. 元資料の根拠と人による採否を固定した20ペア・6資料群以上の評価データを整備する。
2. 登録資料の探索へ計画を接続し、不足項目の追加抽出・追加探索を改訂として保存する。
3. 比較表と評価IDを記事パッケージへ引き継ぎ、原稿検証の件数・版と送信ゲートを更新する。
4. バッチ除外基準の取得と送信直前の競合検査を実装する。
5. 検索サービスの認証・料金・実行環境を確認し、既存の取得制限を通すアダプターを接続する。
6. 人による意味的受入評価と新しい3試作記事を確認してから、本番経路をnewsWeaveのみで有効にする。

既存12項目の検証は変更しない。旧記事を新基準の合格記事へ自動昇格させる経路はない。
この段階の評価結果がeligibleでも、まだ本番の執筆・送信許可として使わない。

## 追加した明示記事連携（2026-10-10）

`EditorialService.comparison(..., selection_audit=...)` に合格監査を明示した場合に限り、具体項目の表と監査を記事パッケージへ引き継ぐ。独立検証・保存記録・現在の資料・実行モデルの再確認と、既存12項目の原稿検証を通す必要がある。検証版は `verification-v10+selection-v1`。shadow設定は引き続き全送信を拒否する。自動候補探索への接続と本番自動経路の切替は未完了である。

今回の送信依頼では適切な資料群が成立せず保留した。具体的な不足・追加確認と730件成功／3件スキップの検証結果は、[計画書の追加対応](comparison-source-selection-improvement-plan.md#14-下書き送信依頼への追加対応2026-10-10-19時台)と `.local/wordpress-draft-preparation-20261010.json` に記録した。既存下書きを更新せず、新しい原稿や投稿も作成していない。
