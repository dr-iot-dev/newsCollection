# 比較項目の動的抽出：設計・実装計画

作成日：2026-10-12（日本時間）

検索用Discoveryの目的を再定義した[新しい改善計画](comparison-discovery-search-vocabulary-plan-20261012.md)を作成した。以下は入力記事群から比較表用候補を作る従来設計の記録であり、検索語彙の新方針は新計画を参照する。
状態：検索に使える短い共通軸へ修正し、IoTの5記事群で10候補、3記事群で7候補を抽出・検索語整理済み。[現行の候補一覧と検索方法](comparison-dynamic-axis-discovery-searchable-20261012.md)を参照。以前の74／58候補は機械的な細分化による過去の出力。

## 目的と工程

未知分野のクラスタリング済み記事群（3〜5件）から、具体的な比較項目を動的に抽出する。資料群の形成は入力側の工程とする。

記事群 → Discovery（項目候補）→ Extraction（各記事の値）→ Selection（採用項目）→ マトリクス判定・記事生成

| 工程 | 責務 | 主な出力 |
| --- | --- | --- |
| Discovery | 同分野で一般的に比較され、語句検索しやすい共通項目を発見する | 項目ID・短い一般名・質問・層・検索語・関連記事ID・記載箇所 |
| Extraction | 候補項目を固定して、記事ごとに値を抽出する | 値・原文根拠・単位・条件・情報の状態 |
| Selection | 抽出結果から採用項目を選ぶ | 採用項目・被覆率・選定理由・不足情報 |
| マトリクス判定・記事生成 | 比較適性と比較方法を判断し、記事にする | 比較表・説明・限界 |

## 設計方針

- Discoveryには項目発見に必要な指示だけを置く。仮回答、対応状態、比較可否、優劣の判断は含めない。
- 「未記載を非対応と判断しない」「提供予定を提供済みと扱わない」等はExtractionの条件とする。金額の順位付けや数値比較の可否は後段で判断する。
- 4層（入力・前提／処理・方式／出力・提供／経済・運用）は探索の観点とする。各層から最低1項目を採る制約は設けない。
- 項目は同分野の製品間で一般的に比較される機能・仕様・提供条件の共通名にする。軸名は24文字以内の短い名詞句とし、括弧・例示・商品名・セット名・長い修飾を付けない。抽象的な評価語は避ける。価格は同一商品内のセット別に分けない。
- Discovery候補に件数の目標・上限を設けない。機械的に分割せず、同分野で独立した一般的な比較項目として扱う内容だけを分ける。一般的な名称のない個別機能群は共通名へまとめ、記事固有の細目を候補数のために列挙しない。採用件数は後段の方針とする。
- 各軸にsearch_termsを付ける。原文に実際にある短い一般語・同義語・表記違い・一般技術語を用いる。コードで軸名と検索語のOR一致を判定し、一致語と関連記事を返す。検索語に商品名・セット名・文章・検索式・広すぎる語を含めない。
- AIを使わないOR文字列検索で2記事以上に出現する候補を残す。これは語句の共有であり、値抽出後の過半数判定とは別に扱う。Discoveryだけを実行するCLIモードを用意する。
- Discoveryの関連記載は候補発見の手掛かりであり、具体情報が抽出できることの確定判定ではない。
- 過半数条件はExtraction後にコードで計算する。独立した比較対象製品数をNとして、必要数は `floor(N / 2) + 1`（3製品：2、4製品：3、5製品：3）。重複発表・転載・補助資料で票数を増やさない。
- 被覆率のほか、同じ質問への回答適合、読者への有用性、重要な差分・共通点、項目間の重複を選定時に確認する。製品別の空欄数も記録する。
- JSONの外枠は固定し、`axes[]` の項目定義と `cells[]` の `axis_id` を動的にする。JSON Schema自体の自由生成は初期実装では行わない。Structured Outputsの形式適合と事実検証は別工程とする。

## Discoveryプロンプト（設計時の概要）

```text
あなたは製品・技術アナリストです。
以下の複数のプレスリリースから、製品・サービスの比較に使える
具体的な比較項目の候補を抽出してください。

【抽出方針】
1. 同分野で一般的に比較される機能・仕様・提供条件の共通項目を抽出してください。
2. 軸名は24文字以内の短い名詞句にしてください。括弧、例示、長い修飾、商品名、
   セット名を付けず、「価格」「通知」「可視化」「外部連携」などの粒度にしてください。
3. 機械的に分割せず、その分野で独立した一般的な比較項目として扱う場合だけ分けてください。
   温度監視セットと設備監視セットの価格は「価格」にまとめてください。
   個別機能群は、一般的な共通名へまとめて構いません。
4. 通常の語句検索でその軸の記載を探せるsearch_termsを付けてください。
   原文にある2〜24文字の一般語・同義語・表記違い・一般技術語を使ってください。
   広すぎる語や商品名、セット名、文章、検索式は避けてください。
5. 4層は探索の観点とし、各層の割当は必須にしません。
   件数の目標・上限を設けず、共通性と検索しやすさを満たす候補を列挙してください。

【各候補の出力】
・項目ID、短い一般名、比較質問、該当する層、search_terms
・関連記載のある記事IDと、その記載箇所

【入力】
記事IDと本文
```

## 実装計画

1. **契約・プロンプトを追加する。** 群単位Discovery用の契約とプロンプトを新設し、項目候補と値抽出結果を分離する。表示用の項目名・質問と、原文一致が必要な検索語も分離する。現行 `ComparisonAxis` は `SearchTerm` を継承しているため、その制約を表示名へ持ち込まない。
2. **3〜5資料の処理経路を追加する。** Discovery → 記事別Extraction → Selectionを実行する。抽出中は候補項目を変更せず、Selectionはその部分集合を採用する。採用後の独立検証で不足が判明した場合は、理由を保存して再選定・資料補充へ戻す。
3. **選定・検証処理を実装する。** 原文参照・項目IDの整合を検証し、過半数条件を計算する。有用性等の意味評価は理由付きで記録する。初期は固定の加重スコアを置かず、根拠・回答適合を確認した候補から選ぶ。
4. **履歴と後段への受け渡しを整える。** 記事群、候補項目、抽出結果、採否理由、モデル・プロンプト版を保存する。採用項目と根拠を既存の比較表・記事生成へ渡せる形式にする。
5. **shadow経路で評価する。** 同じ資料群で現行方式と比較し、根拠の正確さ、回答適合、条件保持、重複、製品別空欄率、入力順による変動、呼出数・費用を確認する。過半数境界、重複製品、項目不足の検証も行う。

主な参照先：

- `app/contracts/comparison_pair_discovery_v3.py`：項目・値・検証結果の契約
- `app/ai/pair_discovery_prompts.py`：現行の計画・値抽出・独立検証プロンプト
- `app/core/comparison_pair_discovery.py`：根拠・被覆率の検証
- `app/orchestration/comparison_pair_discovery.py`：工程実行・履歴・比較資料の出力

現行ペア探索は2資料で軸を固定して第三資料を評価し、被覆率・独立検証は3資料を前提としている。まず群単位の別経路として追加し、既存履歴・方針版を上書きせずに評価する。

数値比較・順位付けの規則、記事成立の最低項目数、既存探索から資料群を渡す方法の詳細は、後続の実装設計で確定する。


## 実装時に確定した点

- Discovery/Extractionは段落IDを参照し、コードで引用・位置を復元する。LLMへ引用文や文字位置の生成を要求しない。
- 選定・抽出・独立検証の項目IDと件数は実行時スキーマでも拘束する。
- 成立判定の既定最低数は3項目。4層・候補数・採用数を埋めるための追加はしない。
- 独立検証で同じ選定目的のまま値・根拠・条件の不備が見つかった場合、同じ候補軸・製品・資料で1巡だけ修正・再選定・再検証する。
- 新経路の出力は比較用資料まで。AI検証通過は記事・公開承認ではなく、原文照合で残った問題を解消するまで自動記事生成への接続は保留する。
