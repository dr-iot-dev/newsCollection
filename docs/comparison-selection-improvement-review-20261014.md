# 3記事比較の自動評価基準とPR TIMES発信元IDの改善検討

作成日：2026年10月14日。対象：第1〜第20候補の保存済み入力・選定評価・記事作成記録。追加のOpenAI API・ローカルLLM推論・埋め込みAPIは実行していない。

## 結論

自動選定には、比較として成立する候補を過剰に保留する要因がある。特に、対象特定・根拠抽出の不確かさを記事全体の不適格へ波及させる設計と、3記事すべてで同じ項目キー・単位・条件を満たすことを要求する設計は改善すべきである。類似度閾値を一律に下げることだけでは解消しない。

改善の中心は、①記事全体ではなく比較対象の範囲を確定する、②抽出品質と比較適性を別々に判定する、③数値の同条件比較と構成・工程比較を区別する、④根拠付きの共通質問で表を評価する、⑤類似度は候補の優先順位に使い、強い意味的根拠がある低類似度候補を再評価へ回す、という方針である。

一方、今回の完成記事は対象限定、原文からの根拠作成、Codexの編集を経ている。12項目passは完成原稿が与えられた根拠と制約に整合したという結果であり、元の自動抽出が正しかったことや、20組すべてが同じ用途の代替製品であることの証明ではない。条件・数値の整合、別製品の機能混入、未記載を非対応にしないこと、重複対象の排除などは維持する。

PR TIMESの企業ID統合廃止は今回実装した。評価ルールの改定は本報告書の提案段階で、元の評価を合格へ書き換えてはいない。

## 2. 現在の判定が過剰な保留を生む仕組み

今回の選定実験は、主に[保存済みローカル実行器](../.local/comparison-three-article-selection-c05-c30-local-20261013/run-local.py)と[数値選定器](../.local/comparison-three-article-selection-c05-c30-local-20261013/selection-core.py)で行われた。アプリ本体の[比較選定](../app/core/comparison_selection.py)とは同一実装ではない。まず実験側で改定案を評価し、本体へ移す際は契約と既存ルールを別に確認する必要がある。

### A. 状態ラベルに複数の意味が混在する

ローカルの状態はready／unknown／multiple_targetsの3種だが、対象の一意性、用途分類、抽出の不十分さが混ざっている。主対象の名前や引用があってもmultiple_targetsになり、理由にsingle_targetというスキーマ外の語が現れる例もある。実行器は主対象引用の検証をreadyで要求するため、名前あり・引用ありだけで自動復旧してはいけない。今回も45件のうち引用の完全一致が確認できたのは29件で、残りには引用照合の問題が含まれる。

### B. 上流の保留がペア判定を上書きする

どちらかの記事がreadyでなければ、same_targetとcomparableをともにunknownへ変更する。元のモデル判定は保存されるが、対象特定の不確かさと用途の比較可能性がひとつの採用ゲートになる。これにより比較可能な候補を修復する経路が必要になる。同一対象の可能性は引き続き排除・保留する必要があり、元のyesをそのまま採用へ戻す案ではない。

### C. 同じ質問への異なる答えが「共通項目なし」になりやすい

数値選定器では3記事に共通する(axis_key, unit, condition_key)を取り、全3ペアでその軸のcompatibleが必要となる。数値の性能順位には妥当な条件でも、入力情報、結果の出力形式、課金体系、処理する場所などの構成比較では、異なる単位や条件自体が説明すべき違いになる。さらにローカル抽出は固定辞書と最大6項目に限定され、抽出漏れは後の全ペア判定から回復しにくい。

### D. グループ・全ペア・ready・全記事共通軸が重複した必須条件になる

全3記事の共通用途グループ、全3ペアの肯定、プロフィールready、共通2項目と差異1項目、類似度閾値を全部ANDで要求する。同じモデルの同じ抽出不足から生じた複数の保留を独立の裏付けとして積み上げやすい。MMRは通過候補の順位付けなので、入口に候補が残らない状況を重み調整で救うことはできない。

## 3. 改善案

### 優先1：対象を記事から切り出し、抽出の状態を分離する

比較単位を「記事全体」から「記事内の根拠付き対象範囲」へ変更する。対象は1製品、明示されたシリーズ、特定機能、導入構成などを区別し、元の記事IDと対象範囲IDを両方保存する。Roborockの特定機種、ServiceNowの1構成、XIAOのSenseなどの対象限定をモデルが提案できるようにする。

対象ごとに名称・型番、範囲、含める機能、除外する別製品、根拠引用と文字位置を保持する。事実ごとの対象帰属を検査し、他機種の値を混ぜない。候補範囲を作れても複数製品を1製品へ統合したり、同一記事の切り分けを独立した3資料として数えたりしない。

状態は、処理成功、対象特定、引用照合、比較適性、執筆可否、完成原稿検証へ分ける。readyは主対象・根拠のチェック結果から算出し、モデルの曖昧な自己申告だけで決めない。multiple_targetsだが他対象が空、理由では単一対象と述べる、一般カテゴリ名を製品名にしている等は「出力不整合」として限定修復へ回す。引用不一致も含め、確認前にreadyへ昇格させない。

### 優先2：比較の種類と読者の判断を先に定義する

|モード|読者が判断すること|適合の条件|
|---|---|---|
|代替選択の比較|同じ仕事にどれを採用するか|具体的な用途と役割が3対象で成立し、異なる選択肢として意味がある|
|構成・工程の比較|どの工程をどの仕組みで支えるか|対象・入出力・前後工程の関係を説明でき、代替品や性能順位に見せない|
|関連技術の紹介|共通テーマの取り組みを知る|比較に必要な共通の判断が作れなければ、比較記事の候補とは分ける|

直接の代替品だけを自動比較として扱うと後半候補を過剰排除し、工程が近いものを何でも同じ比較にすると強引な組を増やす。モードを付け、代替比較を優先順位の上位に、工程比較は読者の具体的な判断が説明できる場合に別枠で扱う。順位9を固定の境界にはしない。各組をモードと根拠から判定する。

全3ペアの独立した肯定は、代替比較では有力な確認になる。工程比較では単なるペア多数決やA→B→Cの関連だけで通さず、3対象を一度に見た具体的な共通目的・担当工程・限界を要求する。共通語がAI・IoT・効率化だけなら採用しない。

### 優先3：項目キーの一致から、根拠付き質問の充足へ変える

まず「何を入力するか」「結果を誰がどう確認するか」「どこで処理するか」など、その3対象で読者が判断する質問を作る。質問は原文の内容に応じて生成し、固定の価格・セキュリティ・精度の全項目を必須にしない。抽象的な「特徴」「メリット」だけで表を埋めることも認めない。

同じ質問に異なる形式・方式・課金単位で答えることは許容する。値・単位・税・時期・提供段階を保ったまま並べ、比較不能な数値の換算や優劣は行わない。数値を大小で評価する行に限って、指標・測定条件・単位・対象範囲の一致を必須とする。

初期の試行ルールは、少なくとも2つの有用で独立した質問、少なくとも1つの選択や工程設計に関わる実質的な違いを要求する。各行は3資料中2資料以上の根拠を持ち、各対象にも複数の確認済み回答があることを確認する。読者の判断に不可欠な質問だけを必須にし、その欠落は保留する。多数派の根拠があっても残る対象の不明を埋めず、「資料で確認できず」とする。これらは検証前の案であり、このルールで20組が自動通過すると主張するものではない。

### 優先4：類似度とMMRを候補探索へ位置付ける

0.55を完成記事の品質保証の境界にはしない。高類似度でも対象や根拠が不適切な例があり、低類似度でも第5候補のように他の判定が成立する例がある。類似度は優先順位と再評価対象の絞り込みに使い、対象・用途・根拠が明確な低類似度候補は別経路で再評価する。

初回の比較実験では0.50／0.55／0.60／0.65を候補探索条件として比較する。0.50への一律変更を決定済みとはしない。全件の全組合せ推論を増やす前に、近傍候補と意味の明確な例外へ予算上限付きで追加抽出・三者判定を行う。MMRは必要条件を通過した候補の関連性・重複抑制に使い、上流の状態不整合の対策として調整しない。

### 優先5：不明を理由別に扱い、必要な部分だけ再判定する

unknownを、主対象未確定、引用不一致、辞書に用途なし、属性抽出不足、条件不一致、処理失敗に分ける。不足している対象範囲や質問に対応する原文だけで追加抽出し、実行の入力・元判定・修復判定・変更理由を残す。すべてのプロフィールと全ペアを毎回やり直さない。

修復回数・推論要求数・時間には上限を設け、解決しない場合は保留を残す。処理失敗や抽出不足を「比較できない」という確定的な否定と区別する。固定辞書は候補提示に使い、辞書外の具体的な用途は根拠引用付きで追加提案できるようにする。

## 4. 12項目検証で不足する評価

現在の12項目は、事実根拠、タイトル、簡潔さ、従来比較、競合比較、比較条件、表、主張の帰属、出典リンク、権利への配慮、独自表現、個人情報である。これらは維持する。ただし「読者がこの3者を並べて何を決められるか」「3者目を足すことで判断がよくなるか」を独立に評価していない。

完成原稿の検証とは別に、執筆前の三者適性判定を設ける。判定者には、①具体的な読者と判断、②同じ役割か異なる工程か、③3者目の必要性、④説明可能な差、⑤無理に広げた共通目的がないかを答えさせる。比較の種類と制限も独立判定へ入力する。12項目passと「代替比較に適合」を別の出力にする。

モデル判定だけで最終的な正解ラベルを作らず、読者価値は人の段階評価でも確認する。同系列の別モデルや同じ根拠パッケージには共通の見落としが残る。また、今回の20本は人が選び、根拠を整理し、編集してから検証した成功例である。未採用例・無編集の自動処理結果を含まないため、選定全体の誤採用率・見逃し率は算出できない。

## 5. 評価・導入の進め方

1. 保存済み20組を診断用の回帰事例にする。第1〜第9候補程度の読者価値、第10〜第20候補の境界は、ユーザーの意見を参考に人が再ラベルする。モード、対象限定の妥当性、要編集量を別に記録する。

2. 未採用組から、高類似度だが用途が違う例、同一製品の別発表、親子型番、シリーズ仕様混入、価格条件不一致、工程が補完関係の例、無作為例を追加する。20組に合わせた調整だけで評価しない。

3. 学習・調整用と未使用の評価用をクラスタ単位で分割する。同一記事や同一製品の別発表が両側へ漏れないようにする。固定した同じ母集団で現行と改定案を比較する。

4. 変更を、状態修復、対象範囲化、質問ベース表、比較モード、類似度の扱いの順に分けて試す。各変更が回復させた候補と新たに誤採用した候補を記録する。引用の有無・条件・対象の整合を確認せずに状態だけ置換する試験結果を採用しない。

5. 評価指標は、読者評価で比較可能な組の再現率、採用候補の適合率、抽出失敗率、未確認値の補完・対象混入件数、無編集初稿の12項目通過率、完成までの編集量、候補当たりの要求数・費用を分ける。全工程の自動化が目標なら、編集後のpassだけを成功率に使わない。

6. 適合率や読者価値を保ったまま再現率を上げ、根拠・条件の違反を増やさない改定を選ぶ。数値の採用目標は人のラベルを作ってから決める。最初は既存判定を置き換えず並走保存し、差分を確認してから本体の契約・実行器へ反映する。

## 6. PR TIMES企業IDの扱い：実装済み

ユーザー指定に従い、同じ公式社名でも別企業IDを統合する処理を廃止した。[実装](../app/orchestration/extraction_organizations.py)の方針版はprtimes-company-id-latest-publication-v2。従来の関数名canonical_organizationsは呼出し互換のため残し、元の配信IDを保持・復元する処理へ変更した。社名の正規化や一致を選定単位に使わない。

今後の選択単位はPR TIMESのcompany IDである。同一ID内でdatePublishedが最も新しい1記事を残す。更新日時dateModifiedは使用せず、時刻同値の処理は従来どおりリリース番号、記事IDで決定する。同じIDで社名が変わっても1件、同じ社名でIDが違えばIDごとに1件を残す。この方針は日立以外にも適用する。

保存済みの1,000記事と公式HTMLの監査DBを使い、新方針で別の出力先へ再選択した。追加取得・埋め込み・クラスタ再計算は行っていない。
