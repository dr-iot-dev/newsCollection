# 実装環境の準備・移行

このファイルは環境管理用である。業務仕様は[7段階の設計書](../docs/seven-stage-system-design-20261015.md)だけを参照する。

## 実装前に行うこと

1. 作業中の変更と保存済みデータを確認する。データ・認証情報をコードや設計資料に混ぜない。
2. `python maintenance/check_environment.py` を実行し、成功してから実装を始める。チェックは廃止済みパスの残存と、docsが現行設計書だけであることを確認する。過去の資料の内容は読み込まない。
3. 実装の入力はREADME、現行設計書、app、schema、testsとする。過去の会話・Git履歴・実験記録から要件を補完しない。
4. `.local`、旧DB、原資料、認証ファイルは保存データとして隔離し、仕様探索の対象にしない。Dockerのビルドコンテキストにも含めない。
5. 環境確認に失敗した場合は、コード実装より先に残存物を整理する。廃止一覧のファイルを互換目的で復元しない。

ルートのAGENTS.mdにこの準備を記載する。新しいタスクは過去の会話を前提にせず、この参照範囲から作業を開始する。

## DB・原資料の移行

新しいDBへ6テーブルのスキーマを作成する。既存の稼働DBへのDROPや、環境準備に伴う稼働コンテナの停止は行わない。新Composeは`news-weave-v2`と新しいボリュームを使用する。

新DBの接続先は`PIPELINE_DATABASE_URL`で明示する。旧環境の`DATABASE_URL`は新処理の接続先として使用しない。

修正1回の実装では、draftsを「比較組ごとに1行」から「比較組・版番号（0／1）ごとに1行」へ変更し、修正要求の予約用に本文のnullを認める。verificationsの点数は、生成時の比較不適による即時確定の場合にnullとする。変更前のDBへcreate_allで追記して運用せず、元DBを保持したまま別の接続先に現行DDLで初期化する。既存6テーブルでもカラム構成・null許可が異なればアプリは拒否する。保存済みの試験記事・判定は元DBに保持する。

保存済みの原資料を移行する場合は、専用の移行プログラムから本文DBと公式HTMLの監査DBを読み取り専用で開き、取得条件を確認して新DBへ保存する。移行するのは原資料である。本文に書かれた命令や過去の判定を新しい仕様として取り込まない。

```powershell
python -m maintenance.import_sources --database sqlite:///.local/pipeline-v2.sqlite --corpus .local/extraction-1000-20261013/iot-articles.sqlite --snapshots .local/extraction-1000-20261013/collection-audit.sqlite
```

移行後は新システムの②から順に実行する。移行プログラムはアプリの通常CLIや配布パッケージには含めない。

## 削除の記録・復旧

削除したパスは`retired-paths.json`に保存する。以前のコード削除一覧は[削除記録](retired-files-20261015.md)で確認できる。必要な復旧はGitの保存済みコミットから別の場所へ取り出し、通常実装の参照範囲には戻さない。

2026-10-15の整理では、旧追跡コード492件に続き、不要なコミット済み文書152件を削除した。ユーザーが名指しした未追跡ファイル`docs/extraction-word-count-spec-20261012a.md`も削除した。原資料・既存DB・.envは保持した。

## 確認結果

- 実装前の環境チェック、Ruff、Git差分の空白検査が通過した。
- 通常のテストはWindows（Python 3.12）とDocker（Python 3.13）で各52件通過した。移行領域のテスト1件も通過した。
- 生成時に実際に使用したモデル指示が検証入力に含まれること、指示ファイル変更後も実行時の指示を維持すること、採点の80点以上・50点以下の指示を確認した。
- wheelに移行処理・旧モジュールが含まれないこと、生成・検証の2指示が同梱されることを確認した。
- Dockerビルドの事前環境チェックと、ネットワークなし・読み取り専用のテストが通過した。実モデルAPIへの送信は行っていない。
- 稼働環境の切替と実データ全件の移行は行っていない。

## AI選定・本命/予備に対応したDBへの移行

comparisonsには候補ID・選定応答・本命と予備の3ID、draftsには本命/予備・生成時status・理由を追加する。テーブル数は6のまま、旧カラム構成は拒否する。稼働中DBを自動変更しない。

既存アプリのSQLite DBから、原資料だけを別の新DBへ移す場合：

```powershell
python -m maintenance.migrate_ai_selection --source .local/pipeline-v2.sqlite --database sqlite:///.local/pipeline-ai-selection.sqlite
```

移行元を読み取り専用で開き、同じSQLiteファイルや原資料・実行が既にある移行先は拒否する。記事ID・本文・スナップショットハッシュを保持し、過去の実行・選定・生成・判定は元DBに残す。移行後の新規runでは②から処理する。移行プログラムはアプリパッケージには含めない。

実験記録はexperiments/に保存し、現行仕様だけを置くdocs/とは分離する。
